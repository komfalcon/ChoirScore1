## M1: API auth, users, and data

- **Persistence:** Use the configured libSQL/Turso client through a Drizzle-backed repository interface. Apply numbered SQL migrations transactionally at API startup and record applied files in `schema_migrations`; keep connection/configuration outside route modules.
- **M1 schema:** Store timestamps as ISO-8601 UTC text. Enforce roles, voice parts, active/forced-change flags, username uniqueness, non-negative AI limits and foreign-key/index constraints in the initial migration. The PRD's score/AI data tables are schema foundations only; M1 does not add score, MusicXML, or AI routes.
- **Password hashing:** Add `bcryptjs` because the scaffold had no password-hashing library and a pure-JavaScript bcrypt implementation is deployable without native build tooling. Hash at cost 12; generated account passwords use a readable unambiguous alphabet. Reject user-selected passwords over 72 UTF-8 bytes so bcrypt cannot silently treat distinct long inputs as the same password.
- **Session tokens:** Build HS256 JWT signing/verification with Node's `crypto` rather than adding a JWT dependency. Keep the token solely in a 7-day Secure, HttpOnly, SameSite=Lax cookie; reload the user from the repository on every valid authenticated request.
- **Login throttle:** Persist per-IP-and-normalized-username throttle state in the migration-backed `login_throttle` table. The pair key is SHA-256 hashed; an atomic libSQL write transaction allows the first five attempts in a fixed 60-second window and makes the sixth start a 15-minute lockout. Expired rows are pruned during login attempts. Same-process writers are serialized to avoid local SQLite contention, and `SQLITE_BUSY` receives bounded exponential-backoff retries with jitter; retry exhaustion fails closed without committing a partial counter update. There is no process-local 10,000-pair cap, and restarts do not clear an active lockout. Replicas share the state only when they use the same shared libSQL database; separate local SQLite files are not shared. The configured database must support writes for logins. Tests cover concurrent attempts across two repository instances, busy-retry exhaustion/recovery, process-restart persistence, threshold/recovery, and 10,000 pre-existing active pairs. Deployment topology, production Turso/Pxxl lock behavior, and the actual trusted-proxy hop count remain unverified; do not treat source-IP attribution or replica behavior as deployment-verified.
- **Password contract:** User-supplied account-creation and changed passwords require at least 8 characters and no more than 72 UTF-8 bytes. Measure the upper bound after UTF-8 encoding, not with JavaScript string length, so bcrypt cannot silently truncate distinct inputs.
- **Audit scope:** Successful admin actions (including existing audited reads) retain their audit entries. Authenticated `/users` and `/admin` mutation attempts, plus active-admin score mutations, retain durable audit rows for success, rejection, and failure, with a resolved actor, target, action, outcome, and safe error code; failure detail is `{}` and successful mutation audit inserts remain in the state-change transaction. Requests denied without a valid actor—including anonymous CSRF, origin, and authentication denials—never create permanent null-actor audit rows. They use fixed-category, in-memory security-event aggregation: at most one redacted warning per category per minute, with only a safe reason code and count; anonymous denial request logs omit path/request identifiers. No request bodies, headers, cookies, IPs, usernames, secrets, or exception messages are recorded in these security summaries.
- **CSRF/CORS/logging:** Require the exact `X-Requested-With: choirscore` header on every state-changing method; accept only exact configured origins; enable Helmet; log request id/method/path/status/duration without request bodies, headers, cookies, credentials or exception messages.
- **Test databases:** Use isolated file-backed libSQL databases for server integration tests so schema migration and transaction behavior is exercised across persistent connections.
- **Status:** The API-backed M1 create → forced-password-change → deactivate → immediate-next-request-denial acceptance passed on integrated `main` at `f185f8f71b4aeb3abc34a10b0a27ca465969df57`, using a fresh, disposable file-backed SQLite database and in-process API requests; the exact-main API suite passed 31/31 tests. This lifecycle acceptance run itself does not verify cross-process contention. Separately, the API suite's competing-writer test uses two repository instances in one Node process, where a process-level write queue serializes writers; it also does not establish cross-process contention or real Turso/Pxxl locking. This is local API evidence only, not browser or deployed-service validation. The owner-deferred Vercel-to-Pxxl check remains pending, not passed.

## M2 API follow-on (local implementation)

- **Score route persistence:** Score visibility is filtered in the SQL list query before search, sorting, or pagination. The current user's grant presence and its `canEdit` value are loaded separately so read-only shared recipients can view without edit permission. Access-list replacement, metadata patches, and version-pointer updates recheck active status and current actor/score permissions inside immediate write transactions; leaving `shared` atomically clears grants so re-sharing starts empty.
- **List cursors:** The `updatedAt DESC, id DESC` cursor is base64url JSON authenticated with HMAC-SHA-256 using the API JWT secret. It is bound to caller ID, query filters, and page size; cursor tampering, cross-user reuse, and scope changes are rejected.
- **Score import:** The API uses Busboy to stream multipart requests with a 6 MiB file cap, bounded field/part counts, and a total-body ceiling. It uses yauzl in lazy-entry mode and never extracts MXL paths to disk. Paths are checked for absolute/traversal forms, backslashes, duplicate entries and symlinks; the archive is limited to 256 entries and 12 MiB aggregate declared expansion, the container to 64 KiB, and the selected score to 6 MiB. `fast-xml-parser` is a direct API dependency for parsing the restricted `META-INF/container.xml` document with entity processing disabled. These dependencies are justified by bounded streaming ingestion and safe, non-extracting MXL reads.
- **Content versions and preservation:** `POST /scores/:id/versions` implements the PRD immutable-save route using the existing shared model and converter contracts. The stored source's converter sidecar is retained server-side for conversion. When an edit changes opaque preserved content, `PRESERVATION_CONTEXT_CHANGED` is returned publicly as HTTP 409 `SCORE_CONTENT_READ_ONLY`; raw viewing/export and separate title/composer/visibility changes remain allowed. Clean content edits create a canonical new MusicXML version.
- **Scope:** API authorization, upload, detail/list, metadata/access, version-save and MusicXML-export handlers have local integration coverage. This does not complete M2: the responsive library/OSMD viewer and end-to-end desktop/phone acceptance remain outstanding. No environment, hosting or deployment checks were run; the owner-deferred configuration checks remain pending.

## M5: autosave persistence and API

- **Version classification and migration:** Add `score_versions.version_kind` (`explicit` or `autosave`), plus nullable autosave request/base-version identifiers. Migration 0004 backfills all existing rows as `explicit`, preserving existing user saves and imported initial versions. A partial unique index scopes retry keys by score and actor; an ordering index supports bounded retention.
- **API contract:** `POST /scores/:id/autosaves` accepts `{ model, baseVersionId, requestId }` under the existing authenticated, CSRF-protected API. A draft is applied only when its base matches the current version. Identical retries return the prior autosave without moving the current pointer; reusing a key for different content/base returns `409 IDEMPOTENCY_KEY_REUSED`; stale bases return `409 VERSION_CONFLICT`. Unchanged drafts return `200` without creating a version row. Their separate receipt window keeps the 20 most recently accepted unchanged request identities per score across actors, ordered by monotonic insertion sequence; the oldest expires on overflow, and retries do not refresh retention. Receipts store the base and canonical payload hash, do not count toward the 20-version cap, and an expired key may be reused.
- **Retention and atomicity:** Keep at most 20 autosave rows per score, pruning oldest autosaves only; explicit versions are never pruned by this policy. Insert, current-version update, pruning, and successful admin audit entry share one database write transaction. A transaction failure rolls back all changes, retaining the prior current version and source. The limit is per score across editors, while retry keys are scoped per score and actor.
- **Scope boundary:** This slice adds API persistence, shared request/response schemas, docs, migration, and tests only; it does not change editor components or `ScoreViewPage`.

## M4: transposition and range-fit clarifications

- Transposed pitches prefer a spelling matching the resulting global or explicit measure key. When the conventional interval spelling exceeds the model's double-accidental limit, use an equivalent bounded spelling; reject only if no supported spelling exists.
- A note outside the comfortable range but inside the hard range costs 1 point. A note outside the hard range costs 5 points total: since it is already counted outside comfortable, add only 4 extra points rather than adding a separate 5-point surcharge.
- `perPart` results use a null-prototype record so every valid part ID, including `__proto__`, is stored as an ordinary own key.
- Persisted range profiles always use canonical S/A/T/B keys. The M4 boundary maps actual model part IDs only through an exact canonical ID or exact case-insensitive canonical name (so MusicXML P1–P4 use their names); missing, conflicting, duplicate, or unrecognized identities make fit unavailable. Member `voicePart` is resolved to an actual score-part ID, and that ID remains the scope key through Apply.
- Manual target-key selection and note-level preview are local and source-immutable. Out-of-range preview notes are red and carry text/accessible range-status labels; Apply is the only path that sends a fresh transposed model to its caller.

## LARGE_LEAP validator conventions

- `LARGE_LEAP` compares consecutive pitched events within each actual part/staff/voice timeline, ordered by score measure number and then resolved onset. It uses the absolute diatonic interval number (`abs(letter-and-octave distance) + 1`), independent of direction and chromatic alteration: exactly a sixth is clean in Alto/Tenor, exactly an octave is clean in Bass, and larger intervals warn. Bass warns only above an octave. Soprano is intentionally not checked because PRD §10.4 specifies no S warning.
- Notes at one resolved onset form one event. Its anchor is the first non-chord pitched note in source order, falling back to the first pitched note if the group has only chord-marked notes; other chord tones are not sequential melodic endpoints. Rest-only onsets are skipped as endpoints, so the adjacent pitched events on either side are compared.
- A `tie: true` anchor followed immediately in the same stream by a same-spelled pitch is treated as one sustained event, not as another leap endpoint. An intervening rest onset breaks tie-continuation merging, while rests remain skipped as comparison endpoints. Warnings locate the destination note using its actual score-part ID, measure number, and one-based beat.
- Canonical SATB mapping failures fail closed as one located `VOICE_MAPPING` error with no leap warnings, matching the existing validators. This validator is intra-part and does not invoke cross-part measure-identity checks.

## PARALLEL_FIFTHS / PARALLEL_OCTAVES validator conventions (Tom's v0 proposal)

- Check all six unordered pairs of distinct canonical SATB parts. Within each part, keep every `(staff, voice)` stream separate and compare the Cartesian product of streams across the two parts.
- A perfect fifth is a spelled generic fifth with exactly 7 semitones; a perfect octave is a spelled octave with exactly 12 semitones. Reduce compounds by octave: e.g. a 12th is in the fifth class and a 15th is in the octave class. A spelled unison is excluded. The same interval class must occur at both endpoints, and both voices must move a nonzero chromatic distance in the same direction.
- Build the union timeline from the two streams' onset events, align events within `1e-9`, and compare only consecutive union events at which both streams have pitched attacks. An unmatched attack, a rest, or a tied same-pitch continuation breaks the chain; do not skip it to find a later common onset. Same-onset chords are represented by the first non-chord pitched note, falling back to the first pitched member.
- Join measures by equal measure number, never by array ordinal. Compare across a boundary only from measure `n` to `n + 1` when both parts have one unambiguous measure for each label. A duplicated matched measure label returns one `MEASURE_IDENTITY` error and no parallel findings. Each parallel finding is an error located at the destination onset, on the first (higher SATB-order) part's actual score-part ID; emit at most one finding per stream-pair transition.
- `PARALLEL_FIFTHS` and `PARALLEL_OCTAVES` are errors, as required by PRD §10.4. If canonical SATB mapping fails, this validator returns one sanitized, located `VOICE_MAPPING` error and no warnings or partial parallel findings, matching the other SATB validators; it skips validation rather than inferring identity.
