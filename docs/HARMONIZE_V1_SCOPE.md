# Harmonize v1 implementation scope

This local slice starts at `838c2e28e9e50f3b121e9ba3344a3b58bcd981f0`. It is **not a claim that PRD §10.7 is complete**.

## Implemented in this slice

- Inline `ScoreModel` request parsing/normalization through the shared strict Zod model, including score key/time structure and deterministic melody-measure duration precheck.
- A feature-specific task prompt and strict generated-output Zod schema. Provider output contains pitches only; requested existing target measures must match the melody's note-count, duration/onset, tie, chord, and tuplet skeleton or the inline request is rejected before provider work. Generated measures explicitly take that skeleton from the melody while retaining target staff/voice and aligned existing lyrics; newly created parts do not inherit melody lyrics.
- Melody tie flags are prechecked for valid source-pitch continuity. Generated target pitches that break a tie continuation are sent through the bounded deterministic repair loop and cannot be accepted unless the tied pitches match. The shared outer and inline Harmonize prompt schemas both enforce the same 4,000-character user-prompt limit.
- Melody selection defaults to the first/top part and must map exactly to soprano (`S`); requested voices default to A/T/B. V1 rejects ambiguous SATB identities, non-monophonic melody streams, and incomplete measure sets rather than guessing.
- A full SATB merge that preserves the normalized source melody part and replaces only requested voice measures. The worker loads the persisted validated voice-range profile and uses it in both the feature prompt and range validator, then runs existing measure-duration, voice-crossing, spacing, parallel-fifths/octaves, and large-leap validators, plus an exact source-melody preservation assertion.
- At most two repair calls after the initial injected provider result. Only a Zod- and validator-approved `{ model, previewOnly: true, chords? }` preview is persisted as a succeeded Harmonize job; polling validates that result again before returning it. Existing job leases, token accounting, ownership checks, and safe failure behavior remain in place.
- **Inline and linked score requests are supported.** A Harmonize submission accepts either an inline strict `ScoreModel` or `scoreId`, never both. For `scoreId`, the API checks the submitter's current view access, hydrates the canonical score snapshot into the job input, and stores the score association; missing and inaccessible IDs use the same non-disclosing `404 NOT_FOUND` behavior. For linked jobs, the worker rechecks current ACL after each provider response and before completion, and verifies the active worker owner, running status, and unexpired database-clock lease before every provider call, including repairs. The worker supplies the optional `authorizeAttempt` callback; Mistral invokes it before every HTTP request attempt, including its single retry. Any future adapter that retries internally must also invoke this callback before each outgoing attempt. Mistral retries retryable transport failures, timeouts, and 5xx responses once (at most two attempts), but suppresses a retry when the fresh callback detects ACL or claim loss. Authorization and network dispatch are not atomic: if access or the worker claim changes after a per-attempt check succeeds but before dispatch, that request may still be sent; an already-dispatched request cannot be recalled. Later attempts are checked again. Completion persistence atomically requires the active claim and current linked-score ACL. Polling rereads the linked job, then checks a fresh active-user/role snapshot and current ACL before returning the refreshed result. The final poll check and response are not atomic: if access or role changes after that check, the result already read may still be returned.
- **ACL revocation and worker-claim loss have different effects.** Migration-backed triggers redact linked input, result, and warnings only when an ACL change actually removes the actor's current view access, including grant removal, visibility/ownership changes, and user role/activity changes. Owners, admins/directors, choir viewers, and retained shared viewers are not redacted; access-list replacement preserves unchanged grants. ACL redaction preserves terminal `succeeded`/`failed` status, `createdAt`, `finishedAt`, and token counts; queued/running jobs are failed with the generic job error and their lease is cleared. Accepted-job quota remains counted from the unchanged `createdAt`. A redacted job's `requestId` remains reserved: because its input is not retained to compare a replay, reusing that ID after access is restored returns `409 IDEMPOTENCY_KEY_REUSED`; a new request needs a new ID. Claim/lease loss without ACL revocation has separate outcomes: only during shutdown, a still-live claim returned after claim acquisition but before `process` starts is released to `queued`. Expired-lease recovery instead marks the running job `failed`, clears result, warnings, token counts, worker and lease fields, leaves input intact, and does not auto-resubmit. When an authorization check observes claim loss, that worker cannot pass later retry/repair or completion checks; however, a request whose attempt check already passed before loss may still be sent, as noted above. Claim loss alone does not trigger ACL redaction, but expired-lease recovery does clear the listed outputs. No database transaction is held open across provider requests.
- **Deletion remains distinct and SQL-only in this slice:** deleting a linked source score causes the database trigger to redact linked input/result/warning/token snapshots and fail every associated job, including previously succeeded jobs. There is no repository score-delete method or HTTP `DELETE /scores/:id` route here; PRD §12 lists that route as planned API surface, not an implemented path.
- Tests use injected providers only. No live provider request or real credentials are used.

## Explicitly not implemented; §10.7 remains incomplete

- **Accept/discard and save:** the validated model is a pollable proposal only. There is no preview UI, playback/sol-fa verification flow, Accept/Discard action, new-score creation, or new-version save. The original score is not modified.
- **Feature breadth / acceptance evidence:** inline and linked scores are supported, but only monophonic soprano melodies are supported here; requested pre-existing target measures with incompatible rhythm skeletons are rejected rather than retimed. Draft/Simplify are unchanged. The §10.7 16-bar 9-of-10 acceptance criterion, playback, and sol-fa rendering are not established by these tests. The distinct §10.7 requirement that generated MusicXML opens in MuseScore is also unverified; it is not the same as the broader §10.3 MusicXML converter round-trip criterion, and that broader criterion does not substitute for MuseScore-open evidence. Existing validators do not expose a standalone `ONSET_MISMATCH` implementation; generated onset/rhythm equality is instead enforced by the pitch-only output contract, the precheck, and code-side melody-skeleton copying.

Do not mark PRD §10.7 complete until the omitted preview/accept/save behavior, plus the remaining acceptance checks, have been implemented and reviewed.
