# Harmonize v1 implementation scope

This local slice starts at `838c2e28e9e50f3b121e9ba3344a3b58bcd981f0`. It is **not a claim that PRD §10.7 is complete**.

## Implemented in this slice

- Inline `ScoreModel` request parsing/normalization through the shared strict Zod model, including score key/time structure and deterministic melody-measure duration precheck.
- A feature-specific task prompt and strict generated-output Zod schema. Provider output contains pitches only; requested existing target measures must match the melody's note-count, duration/onset, tie, chord, and tuplet skeleton or the inline request is rejected before provider work. Generated measures explicitly take that skeleton from the melody while retaining target staff/voice and aligned existing lyrics; newly created parts do not inherit melody lyrics.
- Melody tie flags are prechecked for valid source-pitch continuity. Generated target pitches that break a tie continuation are sent through the bounded deterministic repair loop and cannot be accepted unless the tied pitches match. The shared outer and inline Harmonize prompt schemas both enforce the same 4,000-character user-prompt limit.
- Melody selection defaults to the first/top part and must map exactly to soprano (`S`); requested voices default to A/T/B. V1 rejects ambiguous SATB identities, non-monophonic melody streams, and incomplete measure sets rather than guessing.
- A full SATB merge that preserves the normalized source melody part and replaces only requested voice measures. The worker loads the persisted validated voice-range profile and uses it in both the feature prompt and range validator, then runs existing measure-duration, voice-crossing, spacing, parallel-fifths/octaves, and large-leap validators, plus an exact source-melody preservation assertion.
- At most two repair calls after the initial injected provider result. Only a Zod- and validator-approved `{ model, previewOnly: true, chords? }` preview is persisted as a succeeded Harmonize job; polling validates that result again before returning it. Existing job leases, token accounting, ownership checks, and safe failure behavior remain in place.
- **Inline and linked score requests are supported.** A Harmonize submission accepts either an inline strict `ScoreModel` or `scoreId`, never both. A linked request resolves the caller's current view access under the existing score ACL, hydrates the canonical score snapshot, and stores the score association on the job; missing and inaccessible score IDs use the same non-disclosing `404 NOT_FOUND` behavior. The worker rechecks current access before and after each provider request and before completion persistence; the completion update also enforces the access predicate atomically. Polling rechecks current access for linked jobs and returns the same `404` if access is no longer available, but that check is not atomic with sending the response, leaving a check-to-response race.
- **Revocation-redaction assessment and behavior:** migration-backed triggers redact the linked input, result, and warnings when an ACL change actually removes the actor's current view access, including access-list removal/key changes, score visibility/ownership changes, and user role/activity changes. Owners, admins/directors, choir viewers, and retained shared viewers are not redacted if they still have view access; access-list replacement preserves unchanged grants so a retained recipient is not treated as revoked. Redaction preserves terminal `succeeded`/`failed` status, `createdAt`, `finishedAt`, and token counts; queued/running jobs are failed with the generic job error and their worker lease is cleared. Accepted-job quota usage remains counted from the unchanged `createdAt`. A redacted job's `requestId` remains reserved: because its input is not retained just to compare a retry, reusing that ID after access is restored returns `409 IDEMPOTENCY_KEY_REUSED`; a new request needs a new ID. This fences late worker completion because the repository completion update requires the job to remain running under the owning worker and current ACL. The pre-provider ACL check and network dispatch are not atomic: access can be revoked in the interval, and a request already dispatched cannot be recalled. Polling likewise has a check-to-response race if access changes after its final ACL check. No database transaction is held open across a provider request.
- **Deletion remains distinct:** deleting a linked source score causes the existing database trigger to redact linked input/result/warning/token snapshots and fail every associated job, including jobs that had already succeeded. Deletion handling is through the database-trigger/repository path; there is no HTTP score-delete route.
- Tests use injected providers only. No live provider request or real credentials are used.

## Explicitly not implemented; §10.7 remains incomplete

- **Accept/discard and save:** the validated model is a pollable proposal only. There is no preview UI, playback/sol-fa verification flow, Accept/Discard action, new-score creation, or new-version save. The original score is not modified.
- **Feature breadth / acceptance evidence:** inline and linked scores are supported, but only monophonic soprano melodies are supported here; requested pre-existing target measures with incompatible rhythm skeletons are rejected rather than retimed. Draft/Simplify are unchanged. The §10.7 16-bar 9-of-10 acceptance criterion, MusicXML/MuseScore round-trip, playback, and sol-fa rendering are not established by these tests. Existing validators do not expose a standalone `ONSET_MISMATCH` implementation; generated onset/rhythm equality is instead enforced by the pitch-only output contract, the precheck, and code-side melody-skeleton copying.

Do not mark PRD §10.7 complete until the omitted preview/accept/save behavior, plus the remaining acceptance checks, have been implemented and reviewed.
