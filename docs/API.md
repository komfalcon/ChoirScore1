### Shared score validators

The shared package also exports `validateParallelFifthsOctaves`. It checks all six distinct SATB part pairs and their separate `(staff, voice)` streams. `PARALLEL_FIFTHS` and `PARALLEL_OCTAVES` findings are errors located at the destination onset; the same spelled perfect interval class must occur at both consecutive aligned endpoints, with both parts moving nonzero in the same direction. Compounds reduce by octave (12ths as fifths, 15ths as octaves); unisons are excluded. It compares only consecutive union-timeline events with pitched attacks aligned within `1e-9`; intervening unmatched attacks, rests, and tie continuations break the chain. Same-onset chords use the first non-chord pitched note, otherwise the first pitched member. It crosses only unique adjacent numbered measures. A canonical mapping failure returns one sanitized `VOICE_MAPPING` error and no partial findings, matching the other SATB validators.

The exported `ValidationIssueCode` values are `MEASURE_DURATION`, `OUT_OF_RANGE`, `VOICE_MAPPING`, `MEASURE_IDENTITY`, `VOICE_CROSSING`, `SPACING`, `PARALLEL_FIFTHS`, `PARALLEL_OCTAVES`, `LARGE_LEAP`, `MELODY_CHANGED`, `ONSET_MISMATCH`, and `LYRIC_MISMATCH`. A canonical SATB mapping failure is returned as one `VOICE_MAPPING` error with no warnings; the validator does not infer identity or continue with partial mapping. Its message is a fixed, safe diagnostic and does not expose resolver exception text. For a part-specific failure, `part` is the actual score-part ID; for score-level ambiguity, `part` is the lexically lowest implicated score-part ID. In both cases `measure` is that part's lowest-numbered measure and `beat` is `1`. If a range-profile mapping failure has no implicated part, the lexically lowest score-part ID is used.

`@choirscore/shared` exports `Issue`, `ValidationIssueCode`, `ValidationResult`, `validateMeasureDuration`, `validateOutOfRange`, `validateVoiceCrossing`, `validateSpacing`, `validateParallelFifthsOctaves`, and `validateLargeLeap`. Each validator returns `{ errors: Issue[], warnings: Issue[] }`; an issue is `{ part, measure, beat, code, message }`, where `part` is the actual score-part ID, `measure` is the score measure number, and `beat` is a one-based position in the time signature's denominator units. `MEASURE_DURATION` compares each part/measure's timeline extent with `beats × 4 / beatType` quarter-note units. Explicit note onsets are honored; otherwise each staff/voice advances independently, and chord members share the preceding note's onset. The extent is the furthest event end across the measure, not the sum of simultaneous events, so chords and concurrent voices do not inflate duration. A voice may end before the barline because the model permits implicit trailing silence; only the measure's overall extent is checked, producing at most one issue per part/measure. `OUT_OF_RANGE` is an error beyond the configured hard range and a warning outside the comfortable range but within the hard range; endpoints are inclusive and hard-range errors are not duplicated as warnings. `VOICE_CROSSING` compares adjacent S/A/T/B pitches only at shared event onsets, using exact canonical part IDs or names; rests advance their timeline but do not sound, tied note segments remain separate events at their model onsets, and chord members share their event onset. `SPACING` warns when S–A or A–T pitch distance exceeds 12 semitones; exactly an octave is clean. The PRD does not specify temporal alignment for SPACING, so following Tom's prior §10.4 planning recommendation, it compares only same-measure shared note onsets; duration overlap without a shared onset is clean. Both cross-part validators pair parts strictly by equal measure number, never by array ordinal. Before producing any `SPACING` or `VOICE_CROSSING` findings, they return one `MEASURE_IDENTITY` error and no findings when a measure number is duplicated in one part and that same number occurs in its counterpart in a complete configured pair; the issue is located at the duplicated part ID and measure number at beat `1`, selected by part ID then measure number. The same measure number remains valid across different parts. Chord members share an onset, with one warning per voice-pair/onset; the warning locates the upper voice's actual score-part ID and uses deterministic pair wording. Unknown, conflicting, or duplicate voice identities fail closed rather than being inferred. The default S/A/T/B profile is the PRD §10.5 profile. Optional profiles use canonical S/A/T/B keys and map to score parts by exact canonical ID or exact canonical voice name.

`validateLargeLeap` emits warnings only for Alto/Tenor intervals larger than a diatonic sixth and Bass intervals larger than a diatonic octave; exactly a sixth or octave is clean, and Soprano is not checked. Diatonic interval number uses the spelled letter-and-octave distance (`absolute diatonic steps + 1`), so direction and accidentals do not change the classification. It compares events independently per `(part, staff, voice)`, ordered by measure number and resolved onset. Same-onset chord tones share one event anchored by the first non-chord pitched note (or the first pitched note if all are chord-marked); rest-only events are skipped as endpoints. A `tie: true` note followed immediately by the same pitch in that stream is one sustained event. Each warning locates the destination pitch at its actual part ID, measure, and one-based beat. Mapping failures return one `VOICE_MAPPING` error and no partial leap warnings.

`SafeUser` is `{ id, username, displayName, role, voicePart, isActive, mustChangePassword, aiEnabled, aiDailyLimit, lastLoginAt, createdAt }`. `aiDailyLimit` is a non-negative integer or `null`; timestamps are ISO-8601 UTC strings with a `Z` suffix. Passwords and hashes are never in `SafeUser` or ordinary user responses. `Credentials` is `{ username, password }` and is returned only by account creation, bulk creation, or password reset.

### Role and voice-part validation

- Roles are exactly `admin`, `director`, and `member`; voice parts are `S`, `A`, `T`, `B`, and `none`.
- A `member` must use a staffed voice part (`S`, `A`, `T`, or `B`). An `admin` or `director` must use `none`. Create requests default an omitted privileged-user voice part to `none`.
- A bulk row with no role defaults to `member`, and must therefore include a staffed voice part. Any invalid row rejects the complete request before accounts are stored; a persistence failure rolls back the complete bulk operation.
- For `PATCH /users/:id`, changing a role to `member` requires a staffed voice part in the same request. Changing to `admin` or `director` defaults an omitted voice part to `none`; an explicitly supplied voice part must be `none`. A voice-part-only patch is validated against the user's stored role. No member is persisted with `voicePart: none`.

## Authentication

Every state-changing request (`POST`, `PUT`, `PATCH`, or `DELETE`), including login, logout, and password change, requires `X-Requested-With: choirscore`.

| Method and path              | Request                                                                                                                         | Success                                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `POST /auth/login`           | `{ "username": string, "password": string }`; shared schema requires 8+ characters and at most 72 UTF-8 bytes                   | `200 { "user": SafeUser }`                                                                               |
| `GET /auth/me`               | —                                                                                                                               | `200 { "user": SafeUser }` when password change is not pending; otherwise `403 PASSWORD_CHANGE_REQUIRED` |
| `POST /auth/logout`          | —                                                                                                                               | `204` with no JSON body; clears the session cookie                                                       |
| `POST /auth/change-password` | `{ "currentPassword": string, "newPassword": string }`; both passwords require at least 8 characters and at most 72 UTF-8 bytes | `200 { "user": SafeUser }`                                                                               |

A successful login sets a 7-day signed HS256 JWT in an `HttpOnly; Secure; SameSite=Lax` cookie. The cookie is named `choirscore_session`; `COOKIE_DOMAIN` is optional. The token is never returned in JSON. Logout is idempotent for missing/expired cookies; if a valid session is presented, the API re-checks that the account is still active before clearing it.

Passwords are hashed with bcrypt cost 12. User-supplied account-creation passwords and new passwords must contain at least 8 characters and no more than 72 UTF-8 bytes; `currentPassword` on password change is subject to the same 8-character minimum and 72-byte maximum. The byte limit is measured after UTF-8 encoding, not by JavaScript string length. Password change verifies the current password, stores only the new hash, and clears `mustChangePassword`. The byte ceiling prevents bcrypt's 72-byte input truncation from making distinct passwords equivalent. Short and overlong login attempts still receive the same generic `401 INVALID_CREDENTIALS` response and count toward the login throttle.

Login errors for unknown usernames, incorrect passwords, inactive accounts, and out-of-contract password lengths are the same generic `401 INVALID_CREDENTIALS` response. Attempts are counted per IP-and-normalized-username pair: the first five attempts in a fixed 60-second window are evaluated; the next attempt starts a 15-minute lockout and returns `429 RATE_LIMITED`. Successful attempts also count toward the threshold. Throttle state is stored atomically in the migration-backed libSQL database with a hashed pair key, and expired rows are pruned during login attempts. There is no 10,000-pair cap, and an active lockout survives an API process restart. Replicas share the throttle only if they use the same shared libSQL database; independent local SQLite files are not shared. Deployment topology remains unverified, and the trusted-proxy hop count must still be verified for client-IP attribution.

The API reloads the user record for every authenticated request and rejects deleted or inactive accounts. While `mustChangePassword` is true, **only** `POST /auth/change-password` and `POST /auth/logout` are allowed; this includes blocking `GET /auth/me` with `403 PASSWORD_CHANGE_REQUIRED`. The client should use the login response's `mustChangePassword` field to show the forced-change flow rather than requesting `/auth/me` first. There is no signup or email route. Passwords, password hashes, tokens, and one-time credentials must never be logged.

## Bootstrap administrator

On API startup, the migration runner applies numbered files in `apps/api/migrations/` and records them in `schema_migrations`. If and only if the database has no admin, the server creates the initial `admin` from `ADMIN_BOOTSTRAP_USERNAME` and `ADMIN_BOOTSTRAP_PASSWORD`. Both are required in that case; the password must be at least 8 characters and no more than 72 UTF-8 bytes. The bootstrap account is marked to change its password at first login. The server logs a secret-free warning to change the bootstrap password. Bootstrap credentials are never accepted through an HTTP route.

## Users

All `/users` routes are authentication-required and admin-only. `q` is an optional search string; responses contain only `SafeUser` values.

| Method and path                  | Request                            | Success                                                               |
| -------------------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| `GET /users?q=<query>`           | —                                  | `200 { "users": SafeUser[] }`                                         |
| `POST /users`                    | `CreateUserRequest`                | `201 { "user": SafeUser, "credentials": Credentials }`                |
| `POST /users/bulk`               | `{ "users": BulkCreateUserRow[] }` | `201 { "users": [{ "user": SafeUser, "credentials": Credentials }] }` |
| `PATCH /users/:id`               | `UpdateUserRequest`                | `200 { "user": SafeUser }`                                            |
| `POST /users/:id/reset-password` | No JSON body                       | `200 { "credentials": Credentials }`                                  |
| `POST /users/:id/activate`       | No JSON body                       | `200 { "user": SafeUser }`                                            |
| `POST /users/:id/deactivate`     | No JSON body                       | `200 { "user": SafeUser }`                                            |

The API preserves at least one active administrator. `PATCH /users/:id` may not change the role of the last active administrator away from `admin`, and `POST /users/:id/deactivate` may not deactivate that account. These checks are atomic across concurrent user mutations. A rejected change returns `409 { "error": { "code": "LAST_ACTIVE_ADMIN_REQUIRED", "message": "At least one active administrator must remain." } }`. The UI should keep the user's current role/active state and show the message; it may retry after another administrator is active.

Create requests require `displayName` and `role`; `username` and `password` are optional. Bulk rows use the same fields, and a missing row role defaults to `member`. Usernames are normalized to lowercase. When omitted, a username is generated from the normalized display name using a `firstname.lastname` pattern and numeric collision suffix. When a password is omitted, a random 10-character password is generated from an alphabet that omits ambiguous `0/O` and `1/l/I` characters. Supplied passwords must be at least 8 characters and no more than 72 UTF-8 bytes.

Creation, bulk creation, and reset return credentials once in that response. Only password hashes are stored. Reads and updates never return credentials. Successful admin actions, including user list and admin-settings reads, write exactly one audit record; successful mutations insert it in the same transaction as the action. Mutations to scores by an active `admin`—`POST /scores`, `PATCH /scores/:id`, `PUT /scores/:id/access`, and `POST /scores/:id/versions`—also write a redacted audit record atomically with the score change. Authenticated `POST`, `PUT`, `PATCH`, or `DELETE` attempts under `/users` or `/admin`, and active-admin score mutation attempts, retain an audit row when rejected or failed, including CSRF, origin, authorization, validation, and resource denials. These rows contain the resolved actor, target, action, outcome, and safe error code; failure detail is `{}`. Denials with no valid actor, including anonymous or unauthenticated attempts, do not create durable audit rows; they are represented only by bounded, rate-limited security-event summaries with a safe reason code and count. No request bodies, headers, cookies, IPs, usernames, credentials, password hashes, tokens, generated credentials, or exception messages are included in those summaries. Deactivation is enforced on the next authenticated request, even for a previously issued cookie.

## Admin settings

Both routes are authentication-required and admin-only. Account/security/range preferences are managed on Admin Settings; the global AI submission switch appears on Admin Usage and uses this same `PATCH /admin/settings` route. It gates new submissions and does not indicate provider readiness. State-changing requests require `X-Requested-With: choirscore`.

- `GET /admin/settings` → `200 { "requirePasswordChangeAtFirstLogin": boolean, "voiceRanges": VoicePartRanges, "aiGlobalEnabled": boolean, "aiDefaultDailyLimit": nonnegative integer }` (`GetAdminSettingsResponse`). An unset password-change value defaults to `true`; an unset `voice_ranges_json` setting returns the PRD §10.5 defaults: S C4–G5 (hard B3–A5), A G3–D5 (hard F3–E5), T C3–G4 (hard B2–A4), and B E2–D4 (hard D2–F4). Range settings keys are always canonical S/A/T/B, not MusicXML score-part IDs. Global AI defaults to enabled; the daily limit defaults to the configured API default.
- `PATCH /admin/settings` accepts a non-empty subset of `{ "requirePasswordChangeAtFirstLogin": boolean, "voiceRanges": VoicePartRanges, "aiGlobalEnabled": boolean, "aiDefaultDailyLimit": nonnegative integer }` (`PatchAdminSettingsRequest`), rejects unknown keys, and returns the full current settings object with status `200` (`PatchAdminSettingsResponse`). `voiceRanges` must contain exactly S, A, T, and B; each comfortable range must have valid ordered scientific-pitch endpoints and be contained within its ordered hard range. The validated profile is stored as JSON in the existing `settings` table under `voice_ranges_json`; its shared schema and defaults are also consumed by the M4 fit workflow. At the fit boundary only, score parts map one-to-one to these keys by exact canonical ID or exact case-insensitive canonical name; import order, fuzzy names, and ambiguous identities are never used. Fit is unavailable when any required part/profile mapping is missing or ambiguous. The password-change value applies to newly created and admin-reset accounts; it does not clear flags on existing users. Disabling global AI blocks new submissions but does not cancel accepted jobs.

Each voice-part value has the shape `{ "comfortable": { "low": "C4", "high": "G5" }, "hard": { "low": "B3", "high": "A5" } }`; pitch strings use scientific notation, including accidentals where needed.

## Admin AI usage

`GET /admin/usage` is authentication-required and admin-only. It returns `GetAdminAiUsageResponse` and writes the audited action `admin.ai_usage.read`; the response contains aggregate account and daily data only, never job inputs or results. The 30-day window starts at `00:00:00Z` 29 calendar days before the current UTC day and ends exclusively at the following UTC midnight. `requestsToday` counts accepted jobs created during the current UTC day. Each user row includes accepted requests in the window, succeeded/failed/pending counts, and input/output/total token counts for the full window. Each user's `daily` array contains 30 UTC-date request-count buckets, including zero-filled dates. Every account is present even with zero usage. The top-level `daily` array contains exactly 30 UTC-date buckets, including zero-filled dates, with per-day request outcomes and token totals.

## Authenticated voice-range profile

- `GET /settings/voice-ranges` → `200 VoicePartRanges` with the canonical S/A/T/B profile as the direct response body. Any active authenticated account may read it for score-editing tools; the global session middleware rejects anonymous and inactive users. The endpoint returns no password policy or other settings. An unset profile uses the same validated PRD §10.5 defaults.
- This route is read-only. `PATCH /settings/voice-ranges` is not defined; settings edits remain exclusively at admin-only `PATCH /admin/settings`, which continues to validate and persist the complete canonical profile. Non-admin users receive `403 FORBIDDEN` on that admin mutation route.

## Database and M1 boundaries

The API accesses SQLite/libSQL via a Drizzle-backed repository layer. Schema changes are migration-backed. The initial migration defines the PRD data tables and constraints/indexes; M1 added working bootstrap, auth, users, settings, and audit behavior. The M2 shared foundation adds score schemas and MusicXML string converters; the API follow-on implements the routes documented below. The library UI and viewer remain separate work. All persisted timestamps are ISO-8601 UTC strings.

JSON request bodies are limited to 1 MB by default; `/scores` JSON requests are limited to 6 MiB. Multipart score uploads cap the file at 6 MiB and the streamed body at 6 MiB plus 64 KiB. MXL imports are processed without filesystem extraction: archive paths must be relative and traversal-free, archives are limited to 256 entries and 12 MiB aggregate declared uncompressed size, the container document is limited to 64 KiB, and the selected MusicXML document is limited to 6 MiB. DTD/entity declarations are rejected by the shared converter and are not expanded by the container parser. Helmet security headers are enabled. CORS accepts only exact origins from the comma-delimited `ALLOWED_ORIGIN` environment setting; wildcard origins are not used. Requests with no browser `Origin` are not given CORS permission headers.

### Score summary and list semantics

`ScoreSummary` is the exact card payload: `{ id, title, composer, key, time, partIds, parts, partCount, measureCount, visibility, creator, createdAt, updatedAt, isOwner, canView, canEdit, canEditContent, preservation, canManageAccess, canChangeVisibility, canSetChoirVisibility }`. `creator` is exactly `{ id, displayName }`. `key` is `{ fifths, mode }`, `time` is `{ beats, beatType }`; they are normalized from the shared model. `partIds` and `parts` follow MusicXML part order; every `parts` item is exactly `{ id, label }`, with `id` preserving the stable source part ID and `label` derived from source `<part-name>`/`ScorePart.name`. A missing or blank name uses the deterministic one-based fallback `Part 1`, `Part 2`, etc.; IDs remain opaque in score APIs and general score handling. Only the explicit M4 range-fit boundary may recognize an exact canonical `S/A/T/B` ID or exact case-insensitive `Soprano/Alto/Tenor/Bass` name (including imported `P1`–`P4` IDs by name); it does not infer from order or fuzzy labels and fails unavailable on missing, conflicting, or duplicate mappings. `parts[i].id` must equal `partIds[i]`, and `partCount` equals both array lengths. `measureCount` is the maximum measure count across parts. Timestamps are ISO-8601 UTC. `canEdit` is the role/ACL permission; `canEditContent` is effective musical-content permission (`canEdit && preservation.state === "clean"`). `preservation` is exactly `{ state: "clean" | "opaque_constructs_preserved", readOnlyReason: null | "UNSUPPORTED_MUSICXML_CONSTRUCTS_PRESERVED", preservedConstructs: [{ code, path?, partId? }] }`. Opaque constructs force `canEditContent: false` without changing `canEdit`; the summary identifies the read-only reason and typed warning codes/paths. All returned summaries are accessible to the requester (`canView: true`); inaccessible scores are not included. **Offline availability is client-derived cache state and is not an API field.**

`GET /scores` accepts the following independent filters; they combine with AND:

- `q`: trimmed, non-empty, case-insensitive substring search across title and composer (maximum 120 characters).
- `mine=true`: restrict to scores whose creator is the caller. `mine=false` or omission applies no creator restriction; this facet combines with `visibility` and is not an exclusive scope enum.
- `visibility=private|choir|shared`: optional visibility filter. Omission applies no visibility filter.
- `limit`: integer 1–100; defaults to 20. `cursor` is an opaque string and must be sent back unchanged.

Default list scope is **all scores accessible to the active caller**. Stable order is `updatedAt DESC, id DESC`. The response intentionally has no total count: the client continues while `nextCursor` is non-null.

The detail response’s outer `title` and `composer` are the current score metadata. The `model` is the current musical projection, with its title/composer aligned to that metadata. `musicXml` is the stored current-version source and may retain the imported work/creator text if metadata was changed later. The inherited `preservation` and `canEditContent` fields appear in both summary and detail. Read-only imported scores remain viewable and exportable from their preserved raw `musicXml`.

The public HTTP contract for a blocked content write is HTTP `409` with `scoreContentWriteErrorResponseSchema`: `{ "error": { "code": "SCORE_CONTENT_READ_ONLY", "message": string, "preservation": ScorePreservation } }`. This is distinct from the converter’s internal `MusicXmlConversionError` code `PRESERVATION_CONTEXT_CHANGED`, raised when an opaque imported model is changed; the `POST /scores/:id/versions` handler catches and maps it to the public 409 envelope. Route tests cover this mapping. ACL edit permission is checked independently from preservation state; unchanged musical content is rejected with `NO_CHANGES` rather than creating a duplicate version, including for opaque imports, while a changed opaque source cannot be saved. Title/composer/visibility and shared-access changes remain separate metadata/access operations with their normal role rules. `GET /scores/:id`, MusicXML viewing and raw MusicXML export remain allowed.

### Authorization matrix (all score routes require an active user)

| Visibility / actor | View                                                        | Edit score                                                                                        | Manage shared access           |
| ------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------ |
| `private`          | Creator/owner, admin, director                              | Creator/owner, admin, director                                                                    | Creator/owner, admin, director |
| `choir`            | Every active choir user                                     | Creator/owner, admin, director                                                                    | Creator/owner, admin, director |
| `shared`           | Creator/owner, admin, director, and users in `score_access` | Creator/owner, admin, director; an explicit shared user only when that grant has `can_edit: true` | Creator/owner, admin, director |

Role and transition rules:

- `admin` can manage all scores. `director` can create, edit and publish any score. `member` can create a **private** score and edit their own scores.
- A member-created score starts `private`; a member may not create directly as `shared`. Its owner may later `PATCH /scores/:id` to `visibility: "shared"`, then manage explicit grants with `PUT /scores/:id/access`. Admin/director may manage any score; only admin/director may create or change a score to `choir`.
- `isOwner` means the caller is the score creator. `canEdit`, `canManageAccess`, `canChangeVisibility` and `canSetChoirVisibility` are server-computed flags; the last is true only for admin/director. Owners may change visibility between `private` and `shared`; they cannot set `choir`.
- `canEditContent` is distinct from ACL `canEdit`: it is false whenever the caller lacks edit permission **or** opaque MusicXML constructs must remain untouched. A read-only reason does not revoke view/export or metadata/access capabilities.
- `PUT /scores/:id/access` is valid only while visibility is `shared`; otherwise return `409 SCORE_NOT_SHARED`. Changing away from `shared` revokes and clears the prior explicit grants; switching back starts with no grants. Grant recipients must be active accounts. An explicit shared user’s `can_edit` flag governs only that user’s edit permission.
- Read, detail, and export routes return the same `404 NOT_FOUND` for an unknown or inaccessible score ID, so the API does not reveal private score existence. State-changing routes return `403 FORBIDDEN` when a visible score exists but the caller lacks the required permission; edit grants and active status are rechecked inside the write transaction. State-changing routes also require `X-Requested-With: choirscore`.

### MusicXML export headers and filename

`GET /scores/:id/export?format=musicxml` returns the exact current-version MusicXML string (not an export JSON wrapper):

- `Content-Type: application/vnd.recordare.musicxml+xml; charset=utf-8` (`musicXmlExportHeadersSchema.contentType`).
- `Content-Disposition: attachment; filename="<slug>.musicxml"`; `<slug>` is derived from title by Unicode NFKD normalization, lowercasing, stripping combining marks, replacing each run outside ASCII `a-z0-9` with `-`, collapsing/trimming hyphens, truncating to 80 characters, and using `score` if empty. The final ASCII filename matches `musicXmlExportHeadersSchema.filename`.
- Unknown/inaccessible score IDs return the same `404 NOT_FOUND` as `GET /scores/:id`.

### Converter and dependency choices

- The shared package pins `fast-xml-parser@5.11.2` exactly. The converter uses preserve-order parsing so MusicXML event order (including interleaved `note`, `backup` and `forward` elements) is not collapsed into unordered objects; entity processing, HTML entities and parser value coercion are disabled. It serializes canonical XML itself rather than relying on a lossy object-to-XML builder.
- The API uses Busboy for bounded multipart streams and yauzl for lazy, non-extracting MXL archive reads; `fast-xml-parser` is a direct API dependency for the restricted container document parser.
- The converter accepts MusicXML strings, enforces a 6 MiB UTF-8 byte limit and a 256-element depth limit. It strips and never dereferences only the standard external MusicXML partwise DTD identifier; internal entity declarations, internal subsets and other DTDs are rejected. The API import route validates MXL containers, paths, entry counts and decompressed sizes before passing the selected score to the converter.
- Unsupported elements, attributes, and unrepresented values are reported as typed warnings and remain in a private preservation sidecar with the exact original source string. `musicXmlToModel` also returns typed `preservation` metadata; opaque constructs set `state: "opaque_constructs_preserved"`, `readOnlyReason: "UNSUPPORTED_MUSICXML_CONSTRUCTS_PRESERVED"`, and project to `canEditContent: false` in summary/detail while raw source remains viewable/exportable. This includes later clef changes not represented over time (`MID_SCORE_CLEF_CHANGE_PRESERVED`), valid tempo directions after the first global tempo (`ADDITIONAL_TEMPO_MARKING_PRESERVED`), clef octave changes beyond the represented G2 `-1` (`treble8vb`) and ordinary G2/F4 `0`/omitted forms (`UNSUPPORTED_CLEF_PRESERVED`), a movement title not represented alongside a work title (`ADDITIONAL_TITLE_PRESERVED`), and creator credits other than the single modeled composer (`UNMODELED_CREATOR_CREDIT_PRESERVED`). These warnings are present in import-result warning payloads and in `ScorePreservation.preservedConstructs`. Unchanged imports export byte-for-byte. Edited imports with opaque constructs fail closed with the internal converter error `PRESERVATION_CONTEXT_CHANGED`; a sidecar-free model fails with `SOURCE_PROVENANCE_REQUIRED` unless the caller explicitly marks a truly new model with `{ mode: "new-score" }`. The API `POST /scores/:id/versions` route maps `PRESERVATION_CONTEXT_CHANGED` to HTTP `409 SCORE_CONTENT_READ_ONLY` using `scoreContentWriteErrorResponseSchema`; route tests cover the mapping. The converter chooses divisions to represent durations/onsets exactly and nonzero, otherwise rejects with `UNREPRESENTABLE_DURATION`; it reads metronome `beat-unit`/`per-minute` when representable, otherwise warns before using 90 BPM.
- `packages/shared/test/fixtures/musescore-4.7.5-satb.musicxml` is a repo-authored four-part test tune exported by the official MuseScore Studio 4.7.5 Linux build; the `<software>` metadata records that exporter. One valid `<other-notation>` sentinel was added after export solely to assert unsupported-markup preservation. Separate minimal fixtures cover a G-to-F mid-score clef change and a second valid tempo direction after the initial tempo. Tests cover four parts/clefs, normalized key/time, measures, lyrics, ties, triplet timing, security rejection, exact unchanged-source round trips, canonical model round trip, exact warning payload/preservation codes, read-only summaries and blocked edited exports.
- The API follow-on implements list/search/cursor pagination, server-side visibility filtering, import/create, detail, metadata/visibility changes, access-list replacement, immutable version saves with preservation enforcement, and MusicXML download. Route tests exercise authorization, role transitions, shared grants/revocation, valid and unsafe MXLs, size limits, raw export, safe filenames and the 409 preservation mapping. The responsive library and OSMD viewer plus integrated desktop/phone acceptance remain separate; M2 is not claimed complete until those pieces pass together.

## Errors

Errors use `{ "error": { "code": string, "message": string } }`.

- `400 VALIDATION_ERROR` — invalid payload, including role/voice-part mismatch or any invalid bulk row.
- `400 CURRENT_PASSWORD_INVALID` — current password did not match.
- `401 INVALID_CREDENTIALS` — generic login failure.
- `401 UNAUTHENTICATED` — missing/invalid session, or deleted/deactivated account.
- `403 FORBIDDEN` — authenticated user is not permitted to perform the action.
- `403 PASSWORD_CHANGE_REQUIRED` — forced password change is still pending.
- `403 CSRF_HEADER_REQUIRED` — missing or incorrect `X-Requested-With` on a state-changing request.
- `403 ORIGIN_NOT_ALLOWED` — request supplied an origin outside the exact allowlist.
- `404 NOT_FOUND` — requested resource does not exist, including unknown routes.
- `409 USERNAME_TAKEN` — requested username is already in use.
- `409 LAST_ACTIVE_ADMIN_REQUIRED` — role change or deactivation would leave no active administrator.
- `413 BODY_TOO_LARGE` — request exceeded its JSON size limit.
- `429 RATE_LIMITED` — login lockout is active.
- `500 INTERNAL_ERROR` — unexpected failure; internal database details are not returned.

## Score autosaves (M5)

`POST /scores/:id/autosaves` stores a working draft as an immutable version distinct from explicit saves. The endpoint uses the same active-session and edit-permission checks as `POST /scores/:id/versions`, and all state-changing requests require `X-Requested-With: choirscore`.

Request (`createScoreAutosaveRequestSchema`):

```json
{
  "model": {},
  "baseVersionId": "current-version-id",
  "requestId": "client-generated-stable-retry-key"
}
```

`model` is a valid shared `ScoreModel`; `baseVersionId` is the version the draft was based on; `requestId` is unique to one logical autosave and remains stable across retries of that operation. The API canonicalizes the model using the same source-preservation rules as explicit version saves.

Every successful autosave response uses `{ score, versionId, currentVersionId, outcome }`. `versionId` identifies the version associated with this request and may refer to an older version on replay. If `versionId !== currentVersionId`, the replayed model is not the current saved model: clients must not mark it clean or submit a later edit against the newer base automatically. Pause writes, fetch the latest score, preserve the local draft, and require explicit rebase/resolution; any changed or rebased content is a new logical request with a new `requestId` and the latest `currentVersionId` as its base.

Each successful autosave POST by an active admin writes one success audit record in the same transaction, including saved-version and unchanged-request idempotency replays. An unchanged replay remains a `200` `unchanged` response and creates no version row.

| Status                            | Outcome     | Behavior                                                                                                                                                                                                                                                                            |
| --------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `201`                             | `saved`     | A new autosave version becomes current.                                                                                                                                                                                                                                             |
| `200`                             | `unchanged` | Model has no musical changes from its base; no version row is inserted. Identical retries remain unchanged; mismatched key reuse returns `409 IDEMPOTENCY_KEY_REUSED` while its receipt is retained.                                                                                |
| `200`                             | `replayed`  | Same score, actor, request ID, base version and canonical content as an earlier committed request; returns that request's `versionId` without moving the current pointer. If it differs from `currentVersionId`, follow the pause/fetch/rebase behavior above before another write. |
| `400 VALIDATION_ERROR`            | —           | The request body does not satisfy the shared autosave schema; validate locally and do not retry until the draft is valid.                                                                                                                                                           |
| `409 VERSION_CONFLICT`            | —           | `baseVersionId` is stale; reload the latest score but preserve the local draft. Rebase or resolve it before saving; never silently discard it or resubmit against the stale base. Submit any changed/rebased snapshot as a new logical request with a new `requestId`.              |
| `409 IDEMPOTENCY_KEY_REUSED`      | —           | The same score/actor/request ID was used with a different base version or content.                                                                                                                                                                                                  |
| `409 SCORE_CONTENT_READ_ONLY`     | —           | Preserved source content cannot safely be edited; retain the source and disable autosave.                                                                                                                                                                                           |
| `403 FORBIDDEN` / `404 NOT_FOUND` | —           | Caller cannot edit, or score is missing/inaccessible.                                                                                                                                                                                                                               |

Autosaves are classified with `versionKind: "autosave"`; explicit `/versions` and initial score versions are `versionKind: "explicit"`. Retention is **20 autosaves per score**, regardless of actor. Inserting a new autosave, advancing the current pointer and pruning the oldest autosaves are one transaction. Only autosaves are eligible for pruning; explicit versions are preserved. Failed transactions leave the prior current version and source recoverable. Saved autosave request keys are persisted with their version rows. Unchanged outcomes use a separate receipt window of the **20 most recently accepted unchanged requests per score**, across actors. The oldest receipt expires when a new unchanged request exceeds that limit; FIFO order uses an auto-incrementing insertion sequence, and retries do not refresh it. These receipts store the base version and canonical payload hash, create no version row, and do not count toward the 20-autosave version cap. Once a receipt expires, that request ID may be reused.

## AI jobs (M6 lifecycle and provider-routing slices)

The API persists asynchronous jobs in `ai_jobs`. All endpoints require an active authenticated session; state-changing requests also require `X-Requested-With: choirscore`. A caller may poll only its own job; another user's or unknown job ID returns the same `404 NOT_FOUND` response.

| Method and path    | Request                                                                                                                  | Success                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `POST /ai/jobs`    | `{ "requestId": string, "feature": AiJobFeature, "input": feature-allowlisted object }` (`aiJobSubmissionRequestSchema`) | `202 { "jobId": string, "status": AiJobStatus }` (`aiJobSubmissionResponseSchema`)                             |
| `GET /ai/jobs/:id` | —                                                                                                                        | `200 { jobId, feature, status, result, warnings, error, createdAt, finishedAt }` (`aiJobStatusResponseSchema`) |
| `GET /ai/quota`    | —                                                                                                                        | `200 { dailyLimit, used, remaining, available, resetsAt }` (`aiQuotaResponseSchema`)                           |

The first successful `POST /ai/jobs` acceptance returns status `queued`. `requestId` is a stable client-generated retry key, unique per user. The same key and canonicalized feature/input replay the original job without consuming quota; replay returns its current persisted status, which may be `running`, `succeeded` or `failed`. Using the key for different content returns `409 IDEMPOTENCY_KEY_REUSED`. The request body is strictly validated and bounded by the normal 1 MiB JSON-body limit. `input` is persisted but never included in status responses.

`input` uses a strict per-feature allowlist (unknown keys or invalid value shapes return `400 VALIDATION_ERROR` before acceptance): `harmonize` accepts `prompt`, `score` (the strict shared `ScoreModel`), `melody` (sol-fa or other musical text), `key`, and `time`; `draft` accepts `prompt`, `melody`, `lyrics`, `title`, `key`, `time`, and `tempo`; `simplify` accepts `prompt`, `score`, `melody`, and `lyrics`. Text fields are bounded; `key`, `time`, and `score` use the shared schemas. These schemas reject arbitrary nested score fields as well as top-level fields such as user/account identifiers, passwords, tokens, API keys, authorization headers, cookies, or credentials.

Jobs transition through `queued → running → succeeded|failed`. Daily usage counts accepted jobs by their UTC `createdAt` day, including failed jobs; idempotent replays do not count twice. The effective daily limit is the user's `aiDailyLimit` override, else the persisted administrator default, else `AI_DAILY_LIMIT_DEFAULT` (default `20`, also used by `apps/api/.env.example`). A value of zero blocks submissions. `resetsAt` is the next UTC midnight. Admission is bounded to at most two active jobs globally (`queued` plus `running`) and one active job per user; this bounds the accepted backlog and exceeding either cap returns `429 AI_ACTIVE_LIMIT_REACHED`. Separately, the worker executes at most two simultaneous `running` jobs globally and at most one per user. Exceeding the daily limit returns `429 AI_QUOTA_EXCEEDED`.

The audited `PATCH /admin/settings` endpoint accepts `aiGlobalEnabled` and `aiDefaultDailyLimit`. Global AI defaults to enabled. Disabling it blocks new submissions with `503 AI_DISABLED`; it does not cancel already accepted queued or running work. Per-user AI access remains controlled by `aiEnabled`; disabled accounts receive `403 AI_ACCESS_DISABLED`. Other standard errors include `400 VALIDATION_ERROR` and `401 UNAUTHENTICATED`.

On startup, persisted `queued` jobs remain eligible for processing. Each running job has a unique worker owner and a 30-second lease, renewed every 10 seconds; lease expiry is evaluated against the database clock. Startup recovery, worker claims, active-job admission checks, and the worker's periodic sweep fail only running jobs with a non-null owner and an expired lease, using a safe retry message. This reclaims jobs whose leases expire after startup without automatically resubmitting work whose provider outcome is unknown. Any committed runtime reclaim (from a claim, admission check, or periodic sweep) aborts matching local provider work so the worker can use that slot; provider adapters must honor the supplied `AbortSignal`, and late results are fenced from persistence. Unowned running rows (including rows created before lease metadata existed) are left untouched rather than guessed stale; they continue to count against capacity and require operator reconciliation. Worker replicas must share this database to coordinate claims and recovery; separate databases are independent. The worker persists results, warnings, token counts, and terminal timestamps.

On `SIGTERM` or `SIGINT`, the server first stops accepting HTTP connections and drains accepted requests, then stops new worker claims and drains in-flight provider work and terminal database writes before closing the repository. A claim returned during shutdown but not yet started is released to `queued`. Active work continues renewing its lease during the drain; queued jobs remain durable for a later restart. A provider operation that never returns can delay graceful shutdown, with lease expiry remaining the fencing fallback.

The API selects Mistral only when `AI_PROVIDER=mistral` and `AI_API_KEY` is non-empty; absent or unsupported configuration retains `UnavailableAiProvider` without preventing startup. For Mistral, the adapter sends only `{ feature, input }` after re-validating and projecting the allowlisted input above to the official chat-completions endpoint in JSON mode. Thus the submitted musical payload may include a complete score model (title/composer, key/time/tempo, part identifiers/names, note pitches/rhythm, and lyrics), sol-fa/melody text, lyrics, title, musical metadata, and the caller's prompt, depending on feature; request IDs, account/session/profile data, and non-allowlisted fields are not sent. The provider adapter rejects malformed allowlist inputs before network access. Parsed provider content must be a non-null JSON object; null, scalars, arrays, and invalid JSON receive a generic provider error, and the worker independently rejects non-object results before recording success. `AI_MODEL` and `AI_MODEL_LIGHT` select the heavy and light models (documented aliases/defaults are in `apps/api/.env.example`). The adapter uses bounded, abortable requests and fixed safe provider errors; prompts, score/melody/user content, provider responses, and credentials are not logged. `MockAiProvider` remains test-only.

This is provider routing only, not a completed Harmonize/Draft/Simplify pipeline: the current `AiProvider.generate(work)` JSON adapter uses a generic prompt and does not implement feature-specific prompts or output-schema/score/music validation, repair, preview, or accept. The request-side feature allowlist above is input boundary validation only. A returned JSON object is not a validated score proposal. Provider calls are not made by tests; tests inject a fetch stub.
